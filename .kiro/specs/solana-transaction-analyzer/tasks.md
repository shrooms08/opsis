# Implementation Plan: Opsis — Solana Transaction Analyzer

## Overview

Implementation language is TypeScript 5.x on Node 20+, ESM, strict mode, per
tech.md. No build step is required to run the tests; vitest transpiles in memory.

The ordering of this plan is deliberate and inverts the usual scaffolding →
implementation → tests shape. **The fixture recorder and all six recorded
responses come first, before a single decoder exists.** Every later task is
verified against those recordings. Building decoders first and recording
fixtures afterward would mean each fixture was chosen to match code that already
existed, which is the opposite of ground truth.

### How the `expected.json` bootstrap problem is resolved

A golden fixture directory needs both `input.json` and `expected.json`, but
`expected.json` is the canonical serialization of an `Analysis` and cannot exist
until the pipeline can produce one. That circularity is resolved as follows, and
the resolution is a stated part of the plan rather than an accident of ordering:

1. **Task 2.2 records only `input.json` and `meta.json`** for all six cases.
   `input.json` is the verbatim RPC response; `meta.json` records what the case
   covers, the cluster, the recording date, and the outcome filter that selected
   it. Both are committed once and never regenerated. Nothing in `src/` ever
   reads `meta.json`.

2. **All six `expected.json` files are authored later, by hand, in task 9**, at
   the point where the pipeline can fully analyze those cases.
   Authoring means: run the pipeline over `input.json`, read the produced object
   line by line against the recorded response, and commit it only once a human
   has confirmed each field. **A golden file generated by the code it is meant to
   check proves nothing unless a human reads it once.** That review is the only
   manual step in this plan and it is not optional.

3. **Task 4.10 builds the golden harness to tolerate a fixture directory that
   has `input.json` but no `expected.json`**, reporting it as `pending` —
   explicitly not as a pass. A pending fixture is visible in the test output and
   counted, so a forgotten `expected.json` cannot hide.

4. **Task 13.1 flips that tolerance off for the six pinned fixtures**, which in
   v1 is every recorded fixture. Once their `expected.json` files exist, a pinned
   fixture directory missing one becomes a hard failure, and Requirement 14.1
   discovery semantics together with 14.3 and 14.5 file-failure semantics apply in
   full to it. The `pending` state stays implemented and stays described, because
   it is what the harness reports for a directory that has `input.json` and no
   hand-reviewed `expected.json` — the state task 4.10 introduces and task 13.1
   flips off. What it no longer has in v1 is a population: every recorded
   directory is pinned, so a pending report means a pinned `expected.json` went
   missing or a newly recorded case has not been reviewed yet, not that a
   permanent second tier exists.

### Six recorded fixtures, all six pinned

All six cases are recorded in task 2.2 and committed, and **all six carry a
hand-authored `expected.json` in v1** and are asserted end to end:

1. `01-success-cpi-heavy` — a successful CPI-heavy transaction, recorded with the
   `'succeeded'` outcome filter. Also the v0 lookup-table case: 7 writable and 15
   readonly loaded addresses
2. `02-anchor-user-error` — an Anchor user-defined error, `Custom 6040`, resolved
   through the `AnchorError` line in its own log array
3. `03-program-table-error` — an SPL ATA failure, `Custom 1`, where the failing
   program ID selects the table rather than the numeric value. The suite's only
   legacy message
4. `04-unattested-band-collision` — `Custom 5000`, inside the Anchor framework
   band, raised by a program nothing attests is Anchor
5. `06-nested-cpi-failure` — a failure whose failing top-level instruction has
   children
6. `07-unknown-program` — honest degradation: no decoder, no table, no IDL

**An earlier revision of this section claimed nine recorded fixtures split into
six pinned and three recorded-but-unpinned, and named five directories that were
never recorded** — `03-spl-token-error`, `04-anchor-framework-error`,
`05-v0-lookup-tables`, `08-token-deltas-mixed-decimals`, and `09-partial-decode`.
The correction is recorded rather than overwritten silently, because the numbers
in that revision were load-bearing. Their fates differ and are worth keeping
distinct: `05-v0-lookup-tables` and `08-token-deltas-mixed-decimals` were folded
into `01-success-cpi-heavy`; `03-spl-token-error` and `04-anchor-framework-error`
were superseded at the same numbers by `03-program-table-error` and
`04-unattested-band-collision`, which prove the *negative* of what those two
names promised; and `09-partial-decode` was never recorded, which is the one gap
that remains open. The recorded-but-unpinned tier therefore described a set that
turned out to be empty. **Pending is not passing** either
way: the harness counts pending fixtures and prints them, so a directory without
its `expected.json` is visible in every test run rather than quietly absent.

#### The nested-failure coverage gap is closed

Earlier revisions of this plan recorded a gap: the pinned set contained no case
where a transaction fails while the failing top-level instruction has children,
leaving Requirement 5.2's most subtle behavior unpinned. **Restoring
`06-nested-cpi-failure` to the pinned set closes that gap**, and the note is kept
here rather than deleted so the closure is visible rather than looking like the
gap was never noticed. Top-level attribution over an instruction that has children
is now pinned, which was the specific behavior that had no coverage.

#### The coverage gap the pinned set still leaves

**The partial-decode case is absent.** An earlier revision of this section
claimed the gap had narrowed from no case existing to a case existing without an
`expected.json`, and that authoring that one file was the whole of the remaining
work. That was wrong: `09-partial-decode` — a transaction with an instruction
whose name resolves while its payload carries a trailing suffix the decoder does
not consume — was never recorded, so there is no `input.json` for it and no
directory under `tests/golden/`. **Closing the gap needs a recording, not just an
`expected.json`**, which is strictly more work than the earlier revision claimed
and cannot be done offline: it needs a search for a candidate transaction against
a live RPC endpoint through the task 2.1 recorder. Requirement 11.3 — the
`partial` decode variant carrying decoded fields alongside the unconsumed suffix
in `undecodedData` — is therefore **unpinned by any fixture** in v1.

Two things still constrain it, and neither substitutes for a case chosen to
exercise the variant: the type system, which makes the variant unconstructable
without both halves and pins its `confidence` to `'partial'`, and whatever partial
decodes the six pinned transactions happen to contain incidentally. That argument
is unaffected by the case being absent rather than merely unpinned — it was never
an argument about the fixture. What is lost with the recording is the weaker
consolation the earlier revision took: a committed response the harness openly
reports as pending states its own status, where an absent fixture leaves nothing
on disk to notice, and this paragraph is the only thing standing in for it.

### Why expected.json authoring is grouped rather than spread one-per-task

Every recorded RPC response carries `preBalances`, `postBalances`, and
`meta.computeUnitsConsumed`, so every one of the six cases exercises the
lamport balance, token balance, and compute paths regardless of what else it was
chosen to prove. No case is therefore fully analyzable until the analysis layer
(task 8) lands. Authoring any `expected.json` before that point would guarantee
rewriting it, and a rewritten golden file is no longer ground truth. Task 9
splits the six pinned cases into four sub-tasks by which decode capability each
was waiting on, so the hand review stays reviewable in chunks.

### The v1 / Phase 2 line, and what has no v1 task

Per the Phase 2 section of design.md. Two items that were previously deferred
whole now ship in part, so the boundary is stated clause by clause rather than
requirement by requirement:

- **Verbatim log capture ships in v1** (Requirements 21.1, 21.5, 21.6). Task
  4.11 implements `captureLogs`, copying `meta.logMessages` into
  `LogReport.messages` in RPC order, unchanged, and setting the container
  confidence to `full` when present and untruncated, `partial` when truncated,
  `raw` when absent. Requirement 21 is therefore split across the two phases
  rather than deferred whole.
- **Per-line log attribution stays in Phase 2** (Requirements 21.2, 21.3, 21.4).
  `attributeLogs`, `LogAttribution`, the full-depth scope stack, `AttributedLog`
  construction, and populating `InstructionNode.logs` are all out of v1. The
  types exist and stay empty, so `Analysis` does not churn between phases and
  every v1 `expected.json` remains structurally valid afterward.
- **v1 does parse the log sequence, but only to a depth-1 scope boundary and
  only to extract compute values.** Task 4.11 also implements `walkLogScopes`,
  a general depth-tracking scope walker. It attaches no arbitrary line to any
  node. The Phase 2 work is consequently a generalization of machinery v1
  already contains — the same walk with the stack maintained at every depth and
  lines collected into scopes — rather than a fresh start.
- **Top-level per-instruction compute units ship in v1; nested ones do not**
  (Requirement 8.1, partially satisfied rather than deferred). Task 8.4 derives
  top-level values from the depth-1 `invoke [1]` scopes and reports every nested
  instruction as the `available: false` variant with `raw` confidence, naming the
  Phase 2 per-line attribution deferral as the cause. The transaction total
  (Req 8.5) comes from `meta.computeUnitsConsumed` and is unaffected.
- **Nested CPI failure attribution is not implemented** (Requirement 5.5).
  `FailureReport.cpiAttribution` is always `null` in v1. The field stays in the
  type so `Analysis` does not churn between v1 and Phase 2 and every v1
  `expected.json` remains structurally valid afterward. Requirement 5.2's
  top-level attribution is unaffected: it comes from `meta.err`, not from logs.
- **Three correctness properties get v1 test tasks**: numbers 25, 34, and 42,
  which is exactly the v1-essential set design.md now marks. The nine properties
  design.md carries an explicit Phase 2 marker on were previously in the v1 set and
  are deferred; they stay in design.md as the specification of intended behavior
  and are implemented in Phase 2 alongside the properties that were never
  v1-essential.
- **Why those three survive the cut.** Number 25 checks the architecture's central
  data-representation decision: decimal strings and `bigint` arithmetic exist
  specifically to survive lamport values above 2^53, no recorded fixture is
  guaranteed to contain such a value, and a float regression is invisible on screen
  because a rounded lamport balance has the right shape, the right magnitude, and
  the wrong digits. Number 34 *is* the read-only guarantee — the only mechanical
  check behind the claim that no transaction can be constructed, signed, or
  submitted, and without it the claim is documentation. Number 42 checks the
  comparator every golden fixture depends on; a comparator that ignores a leaf
  difference makes all six pinned fixtures meaningless, so it is the one test whose
  failure would invalidate the rest of the suite.
- **What deferring the other nine costs, stated plainly.** design.md selected those
  nine precisely because each, if violated, produces silently wrong output a
  reviewer cannot detect by reading the terminal: a confidence marker aggregating
  upward to `full` over a `raw` child, a signer designation on a lookup-table
  address, an exit code mapped to the wrong class. v1 leans on the six pinned golden
  fixtures for that coverage, and a fixture reaches less far than a property.
  Fixtures pin exact digit strings, so an arithmetic regression on the recorded
  values fails a test — but they exercise only the values those six recorded
  transactions happen to contain. No adversarial base58 signature with leading zero
  bytes, no generated tree shape, no permuted key ordering. Covering the input space
  beyond the recorded examples is exactly what the property tests did, and that
  breadth is what is being deferred.

### Placement of the three property test tasks

Number 25 sits immediately after the unit it constrains, as task 8.2 directly
below the lamport delta implementation, because it ranges over one pure function's
input domain and catching an arithmetic regression at the point of writing is worth
more than catching it three waves later. The other two land in the
verification-hardening wave, because both range over something whole rather than
over a single unit: number 34 quantifies over every call site in `src/`, and number
42 over the golden comparator the entire fixture suite rests on. Task 13.11 carries
a coverage table so each of the three is traceable to exactly one task.

- [x] 2. Fixture recorder and recorded ground truth

  - [x] 2.1 Implement the fixture recorder
    - Create `scripts/recordFixture.ts` with `OutcomeFilter`, `RecordOptions`,
      `FixtureMeta`, `RecordedFixture`, and `recordTransactions` exactly as
      design.md specifies
    - It pages `getSignaturesForAddress` for a program address, keeps the entries
      the outcome filter selects, fetches each with `getTransaction` using
      `maxSupportedTransactionVersion: 0`, and writes the verbatim response to
      `<outDir>/<caseName>/input.json` plus a `meta.json` recording `case`,
      `covers`, `cluster`, `recordedOn`, `signature`, and `outcome`
    - `OutcomeFilter` is `'failed' | 'succeeded' | 'any'`, judged on the `err`
      field of each `getSignaturesForAddress` entry: `'failed'` keeps a non-null
      `err`, `'succeeded'` keeps a null `err`, `'any'` keeps everything.
      `RecordOptions.outcome` has no default at the type level, so every
      invocation states which class it wants
    - **`'failed'` is the ordinary choice** — failure analysis is the primary use
      case and five of the six cases are failures. The exception is
      load-bearing: `01-success-cpi-heavy` requires `'succeeded'`, and **a
      failures-only recorder could not have produced it**, which is why the filter
      exists rather than the `err`-non-null test being hard-coded
    - The exported function is named `recordTransactions`, not
      `recordFailedTransactions`, because the old name contradicts the filter it
      now accepts
    - `FixtureMeta.outcome` records which filter selected the case, so a later
      maintainer can re-record it identically instead of guessing which class it
      came from
    - `recordedOn` is passed in by the caller, not read from a clock, so the
      written bytes are reproducible for a given invocation
    - Four constraints hold, each deliberate: **it makes unsolicited network
      calls by design**, which no other component does — every other call in the
      system answers a signature the user typed, whereas enumerating candidates
      is a search rather than a lookup; **it lives outside `src/`** so the
      Requirement 15 AST guard's scope stays "code we ship" and the package
      exclusion follows from the directory rather than from someone remembering;
      **it is excluded from the published package** by the task 1.1 allowlist;
      and **it is never invoked by the test suite**, which runs with the task 1.3
      interceptor active and would fail it by design. Recording is a manual
      maintainer step, run once per fixture, with the result committed
    - **Every one of those four constraints is unchanged by the outcome filter**,
      which introduces no new capability class: it is a predicate applied to
      results `getSignaturesForAddress` has already returned, so selecting
      successful transactions instead of failed ones changes which responses are
      written to disk and nothing about which RPC methods are called
    - It performs no transaction construction, no signing, and no submission.
      Both RPC methods it calls are read-only
    - _Requirements: 10.2_

## Notes

- Tasks marked with `*` are optional and can be skipped for a faster MVP. Every
  test-related sub-task is marked optional; no core implementation task is.
- The **hand review of each `expected.json` in task 9 is not optional** and is
  the one manual step in this plan. Everything else is executed in the editor.
- The three v1 property tests map to tasks as follows: 25 → 8.2; 34 → 13.2;
  42 → 13.7. Task 13.11 asserts this mapping stays complete. The nine properties
  design.md marks Phase 2 have no v1 task and are implemented then.
- The read-only call-site guard, property number 34, is task 13.2 rather than an
  optional sub-task, because a missing call-site guard removes the read-only claim
  outright rather than merely weakening test coverage.
- Lamport-to-SOL rendering exactness, property number 35, has no v1 task, but it is
  closely tied to number 25, which does: both stand or fall on the same
  `bigint`-and-string arithmetic, and task 8.2 checks that arithmetic directly
  across the full `u64` range. Beyond that, number 35 is covered transitively by the
  six pinned golden fixtures, whose `expected.json` files pin the exact digit
  strings, so a floating-point regression in the conversion fails a pinned golden
  test. It becomes a first-class property test in Phase 2.
- CPI failure attribution, property number 14, is vacuously true in v1 since its
  antecedent never holds under the Requirement 5.5 deferral, which is why no task
  implements it.
- Log conservation, property number 29, is not satisfiable in v1 as written,
  because it quantifies over messages attributed across instruction nodes and
  nothing is attributed yet. It applies to Phase 2. The v1 guarantee in its place
  is weaker but exact: `LogReport.messages` equals `meta.logMessages` element for
  element, in order. That is pinned by the six pinned golden fixtures in task 9
  and by the unit test in task 13.10, not by a property test.
- No task adds a runtime dependency beyond tech.md's four. JSON
  canonicalization, decimal formatting, and Anchor IDL parsing are all
  hand-written for reasons recorded in design.md — decimal formatting in
  particular must not be delegated to a library that might use floats.

### Reading the graph

**Wave 2 is a single-task bottleneck by design.** Task 2.2 records all six
`input.json` files and nothing downstream of it can start until it completes.
That is the ordering mandate made structural: no decoder, resolver, renderer, or
test is written against anything other than a recorded mainnet response.

**Wave 10 is the second bottleneck.** The four `expected.json` authoring
sub-tasks can run in parallel with each other but block every rendering and
verification task, because a renderer built before ground truth exists has
nothing to be wrong against.

**Task 8.2 sits in wave 9, immediately after task 8.1's wave.** It is the only
property test outside the verification-hardening wave, and it is there rather than
deferred to the end because it ranges over one pure function's input domain and an
arithmetic regression is cheapest to catch next to the code that caused it. It
writes only its own test file, so it conflicts with nothing else in the wave.

**Task 4.11 sits in wave 5 despite its number.** It is numbered last in group 4
only to avoid shifting existing sub-numbers, and it has two downstream consumers
that fix its position: task 4.9 in wave 6 emits the `LogReport` it produces, and
task 8.4 in wave 8 consumes its `walkLogScopes`. It shares wave 5 with task 4.8
without conflict, since one writes `src/resolve/logs.ts` and the other
`src/decode/registry.ts`. No wave boundary moved to accommodate it.

Two file-conflict serializations are deliberate rather than dependency-driven:
`src/decode/registry.ts` is written in wave 5 (task 4.8, the `Unknown` fallback)
and extended in wave 9 (task 6.6, the precedence ladder); the golden harness is
written in wave 7 (task 4.10, pending-tolerant) and tightened in wave 14 (task
13.1, strict). Neither pair may share a wave.
