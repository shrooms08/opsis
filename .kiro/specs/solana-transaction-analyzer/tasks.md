# Implementation Plan: Opsis — Solana Transaction Analyzer

## Overview

Implementation language is TypeScript 5.x on Node 20+, ESM, strict mode, per
tech.md. No build step is required to run the tests; vitest transpiles in memory.

The ordering of this plan is deliberate and inverts the usual scaffolding →
implementation → tests shape. **The fixture recorder and all eight recorded
responses come first, before a single decoder exists.** Every later task is
verified against those recordings. Building decoders first and recording
fixtures afterward would mean each fixture was chosen to match code that already
existed, which is the opposite of ground truth.

### How the `expected.json` bootstrap problem is resolved

A golden fixture directory needs both `input.json` and `expected.json`, but
`expected.json` is the canonical serialization of an `Analysis` and cannot exist
until the pipeline can produce one. That circularity is resolved as follows, and
the resolution is a stated part of the plan rather than an accident of ordering:

1. **Task 2.2 records only `input.json` and `meta.json`** for all eight cases.
   `input.json` is the verbatim RPC response; `meta.json` records what the case
   covers, the cluster, and the recording date. Both are committed once and
   never regenerated. Nothing in `src/` ever reads `meta.json`.

2. **Each `expected.json` is authored later, by hand, in task 9**, at the point
   where the pipeline can fully analyze that case. Authoring means: run the
   pipeline over `input.json`, read the produced object line by line against the
   recorded response, and commit it only once a human has confirmed each field.
   **A golden file generated by the code it is meant to check proves nothing
   unless a human reads it once.** That review is the only manual step in this
   plan and it is not optional.

3. **Task 4.10 builds the golden harness to tolerate a fixture directory that
   has `input.json` but no `expected.json` yet**, reporting it as `pending` —
   explicitly not as a pass. A pending fixture is visible in the test output and
   counted, so a forgotten `expected.json` cannot hide.

4. **Task 13.1 flips that tolerance off.** Once all eight `expected.json` files
   exist, a fixture directory missing one becomes a hard failure, and
   Requirement 14.1 discovery semantics together with 14.3 and 14.5 file-failure
   semantics apply in full.

### Why expected.json authoring is grouped rather than spread one-per-task

Every recorded RPC response carries `preBalances`, `postBalances`, and
`meta.computeUnitsConsumed`, so every one of the eight cases exercises the
lamport balance, token balance, and compute paths regardless of what else it was
chosen to prove. No case is therefore fully analyzable until the analysis layer
(task 8) lands. Authoring any `expected.json` before that point would guarantee
rewriting it, and a rewritten golden file is no longer ground truth. Task 9
splits the eight cases into three sub-tasks by which decode capability each was
waiting on, so the hand review stays reviewable in chunks.

### Phase 2 deferrals — no v1 tasks exist for these

Per the Phase 2 section of design.md:

- **`resolve/logs.ts` is not implemented** (Requirement 21). `LogReport` is
  emitted with `present: false`, empty `unattributed`, and `raw` confidence —
  the same shape Requirement 21.6 already defines. No type changes.
- **Per-instruction compute units are not implemented** (Requirement 8.1). They
  are parsed from the `consumed N of M compute units` log line, which is log
  data. Task 8.4 implements only the transaction total from
  `meta.computeUnitsConsumed` (Req 8.5) and emits the `available: false` variant
  with `raw` confidence for every per-instruction value. **This is the log
  deferral propagating, not an omission** — the `available: false` variant
  exists precisely for the case where the number was not supplied.
- **Nested CPI failure attribution is not implemented** (Requirement 5.5).
  `FailureReport.cpiAttribution` is always `null` in v1. The field stays in the
  type so `Analysis` does not churn between v1 and Phase 2 and every v1
  `expected.json` remains structurally valid afterward. Requirement 5.2's
  top-level attribution is unaffected: it comes from `meta.err`, not from logs.
- **Only the twelve v1-essential correctness properties get test tasks**:
  properties 1, 2, 13, 20, 25, 34, 40, 41, 42, 43, 44, 45. The remaining
  properties stay in design.md as the specification of intended behavior.

### Property test placement

The twelve v1-essential property tests are placed next to the implementation
they constrain wherever the unit under test exists on its own (properties 1, 2,
20, 25), and in the verification-hardening wave where the property is over a
whole `Analysis`, the whole `src/` tree, or the process contract (properties 13,
34, 40, 41, 42, 43, 44, 45). Task 13.11 carries a coverage table so every one of
the twelve is traceable to exactly one task.

## Notes

- Tasks marked with `*` are optional and can be skipped for a faster MVP. Every
  test-related sub-task is marked optional; no core implementation task is.
- The **hand review of each `expected.json` in task 9 is not optional** and is
  the one manual step in this plan. Everything else is executed in the editor.
- The twelve v1-essential property tests map to tasks as follows: 1 and 2 →
  4.2; 20 → 4.6; 25 → 8.2; 34 → 13.2; 13 → 13.3; 45 → 13.4; 40 → 13.5;
  41 → 13.6; 42 → 13.7; 43 → 13.8; 44 → 13.9. Task 13.11 asserts this mapping
  stays complete.
- Property 34 is task 13.2 rather than an optional sub-task, because a missing
  call-site guard removes the read-only claim outright rather than merely
  weakening test coverage.
- Property 35, lamport-to-SOL exactness, is covered transitively in v1 by the
  golden fixtures, whose `expected.json` files pin the exact digit strings, so a
  floating-point regression in the conversion fails a golden test. It becomes a
  first-class property test in Phase 2.
- Property 14, CPI failure attribution, is vacuously true in v1 since its
  antecedent never holds under the Requirement 21 deferral, which is why no task
  implements it.
- No task adds a runtime dependency beyond tech.md's four. JSON
  canonicalization, decimal formatting, and Anchor IDL parsing are all
  hand-written for reasons recorded in design.md — decimal formatting in
  particular must not be delegated to a library that might use floats.

### Reading the graph

**Wave 2 is a single-task bottleneck by design.** Task 2.2 records all eight
`input.json` files and nothing downstream of it can start until it completes.
That is the ordering mandate made structural: no decoder, resolver, renderer, or
test is written against anything other than a recorded mainnet response.

**Wave 10 is the second bottleneck.** The three `expected.json` authoring
sub-tasks can run in parallel with each other but block every rendering and
verification task, because a renderer built before ground truth exists has
nothing to be wrong against.

Two file-conflict serializations are deliberate rather than dependency-driven:
`src/decode/registry.ts` is written in wave 5 (task 4.8, the `Unknown` fallback)
and extended in wave 9 (task 6.6, the precedence ladder); the golden harness is
written in wave 7 (task 4.10, pending-tolerant) and tightened in wave 14 (task
13.1, strict). Neither pair may share a wave.
